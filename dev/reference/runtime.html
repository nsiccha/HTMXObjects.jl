HTMXObjects.ERROR_DIR Constant

ERROR_DIR

Directory where HTMXObjects writes per-error log files. Initialized in __init__ from the HTMXO_ERROR_DIR environment variable, falling back to joinpath(tempdir(), "htmxo_errors"). Can be reassigned at runtime.

HTMXObjects.CallerFault Type

CallerFault(status, message; param=nothing)

Throw from a route body when the request itself is at fault: an unknown resource id (404), an argument out of range (400), a refused operation (403, 409). The answer has status (200 under HTMX, so the swap still happens) and shows message: in the default article, titled with the status's reason phrase (Not Found), or through the struct's __error__ hook, which reads status and message from unwrap_error(err). Like every error answer it is recorded: an error log whose header names status, the @error line, X-HTMXO-Error-Id, the error id in the article, and __on_error__.

HTMXObjects.ErrorTexts Type

ErrorTexts

The words of HTMXObjects' error answers: the article that points at a recorded server fault (error, server_fault), the caller-fault articles (titled with their status's reason phrase from reasons, or refused for a status without one, and ending in error_id), the framework's own caller-fault messages, a stalled operation's terminal (run_again, progress) and the page shell's failed-request toasts (request_failed, no_response, timed_out, dismiss, and reasons again), the status line over a part of the page that a running request will replace (loading, loading_named; see request_feedback_script), and the search field of a long choice list (choice_search, its placeholder, and choice_no_match, shown when no option matches; see choice_list). Build one with error_texts.

source
HTMXObjects.KeySubscriptions Type

KeySubscriptions()

Thread-safe registry mapping a resource key (e.g. "gh:owner/repo#12") to the live SSEStreams of the fragments subscribed to it. One instance per app (usually a const): an @sse route body feeds it through serve_key_feed!, and any server code pushes a refresh with invalidate_key!, which re-fetches every subscribed live_fragment on every open page.

source
HTMXObjects.OperationContext Type

OperationContext

Request-local context passed to a RootProvider. scope and key describe the provider-selected application lifetime (:request, :session, or :job); transport is :http, :websocket, or :sse. A custom provider owns any storage behind session/job keys. The managed RootRetention form keeps that common in-process storage inside HTMXObjects.

source
HTMXObjects.OperationPolicy Type

OperationPolicy(mode=:auto; poll_interval="200ms", keep_progress=true, keep_terminal_tree=false, stall_after=600, queued_stall_after=nothing)

Select route execution transport. :auto — the default, applied to every app whether or not it declares a policy — polls pending-capable HTMX requests. A direct rich-page visit spends the same grace budget an HTMX request would: an operation that finishes within it renders inline in its composed __page__ shell — one response, no placeholder, no refetch. Only a slower operation defers, returning the shell with a load-triggered request that joins the already-running operation; that fragment then uses the same grace/polling path. Routes without page chrome stay direct for non-HTMX requests. :polling forces the polling transport. :blocking keeps every route direct; it is the opt-out for a route surface that genuinely must answer inline.

HTMXObjects.RuntimeJob Type

RuntimeJob

One job: a @queued route execution that outlived the :auto grace period (whether it continued in the background while clients polled it or answered inline), or work reported through track_job!. state is :queued, :running, :done or :failed; duration is NaN until it finishes. requests counts the requests that started or joined the same computation, polls the follow-up requests it answered. result_url is the externally visible target of an originating GET whose query needed no token/credential redaction (empty otherwise). progress is the job's progress node (a Treebars tree when Treebars is loaded), kept after completion so history shows per-phase timings. scope is the root-provider scope of the operation that started it (:request, :session, :job, or :none outside any operation); the provider key itself is only kept as a salted in-process digest, used to match jobs_board's mine filter. position is the queue position of a :queued job (0 otherwise); a job whose computation waits in the job queue (configure_job_queue!) is listed as :queued with its current position.

source
HTMXObjects.RuntimeRequest Type

RuntimeRequest

One tracked HTTP request. duration is NaN and status is 0 while the request is in flight. kind is :page, :htmx, :poll (a follow-up operation poll), :websocket or :sse; the last two stay in flight for the life of the connection. route is the matched route pattern ("GET /foo/{1}"), mode the operation transport HTMXObjects chose (:blocking, :polling, :page_load, :poll for a follow-up poll, :preload for a speculative request to a @preload route, :none for non-operation requests), and job the id of the RuntimeJob the request started or polled (0 for none). target is the redacted path and query.

SSEStream

HTMXObjects.collect_and_measure! Method

collect_and_measure!() -> NamedTuple

Run one full GC.gc(true) and return (; at, seconds, rss_before, heap_before, rss_after, heap_after), with byte counts and a Unix completion timestamp. Collections through this API are serialized; only the latest result is retained. Call from an explicit POST action, never a polling GET: a full collection pauses all Julia threads. RSS also includes mapped files, native allocations and code; the post-collection heap is the live Julia data.

source
HTMXObjects.configure_job_queue! Method

configure_job_queue!(; max_running=nothing, abandon_after=nothing, workers=nothing) -> NamedTuple

Bound how many @queued (heavy) computations run at once. Off by default (max_running=0): a @queued computation starts on :default immediately. With max_running=n, at most n such computations run at a time and the rest wait in FIFO order; the runtime dashboard and jobs_boards list them as :queued with their queue position ("queued · #3"), and they start as earlier ones finish. Concurrent requests for the same computation still share it, queued or running.

HTMXObjects.invalidate_key! Method

invalidate_key!(subs::KeySubscriptions, key; event="refresh") -> Int

Push a refresh of key to every subscribed fragment on every open page: each subscribed stream gets one <event>-<key> frame carrying the key, which re-fetches exactly the fragments showing that key through their hx-trigger="sse:<event>-<key>" (see live_fragment) — on a multiplexed live_region stream the other keys' fragments stay put. Streams whose client is gone are pruned. Returns the number of streams notified; a key with no subscribers is a quiet no-op (0).

HTMXObjects.live_fragment Method

live_fragment(key, content...; fragment_url, events_url=nothing, event="refresh", swap="outerHTML", id=nothing, class=nothing)

A fragment that re-fetches itself when key is invalidated. Renders a <div> that re-GETs fragment_url into itself (hx-swap, default "outerHTML") whenever its stream sends the key's event (<event>-<key>, default refresh-<key>). The fragment route answers with the same live_fragment call, so the re-fetch is self-similar.

source
HTMXObjects.live_region Method

live_region(events_url, content...; id=nothing, class=nothing, discover=false)

One shared serve_key_feed! stream for many live_fragments. Renders a <div> that connects a single event stream (sse-connect to events_url, which must carry every key the region shows, e.g. query_url(__self__/"key_events"; key=keys)) and hosts fragments rendered without their own events_url: each re-fetches only on its own key's event. One connection per region instead of one per fragment — the shape for per-row or per-reference liveness, where a stream per fragment would starve the page's other requests under HTTP/1.1's per-origin connection limit.

HTMXObjects.record_error! Method

record_error!(recorder::ErrorRecorder, uid, log_path, req)

Append capture metadata to an already recorded error, then update the recorder's failing-URL index from the HTTP.Request. Pass nothing as req to append metadata only. The error log and response remain owned by HTMXObjects; this side-effect hook neither records another error nor changes the response. Filesystem failures propagate to the framework's hook-failure logger.

HTMXObjects.record_error Method

record_error(err, bt, req) -> (uid, path)

Record a caught, recovered-from error to HTMXObjects' error-log surface (ERROR_DIR[]/<uid>.log, the same sink the ?run=latest error feeds read) and return the short uid and the full path, without aborting the request or rendering an error article. Use it from a route body that caught an exception, handled it (a fallback value, a visible stand-in, a partial result), and still wants the trace to reach the error surface where triage tooling can see it.

HTMXObjects.runtime_dashboard Function

runtime_dashboard(tracker=runtime_tracker(); prefix="/runtime", live=true, refresh="2s", limit=100)

Render the runtime dashboard for tracker: a process summary, the running and the latest limit finished jobs as live job boards (see jobs_board; with Treebars, each with its progress tree), with stable job identity, start/update times, caller counts and inspect/watch/result actions; in-flight requests, per-route timings, and the latest limit finished requests. HTMXObjects.send_ahead Method

send_ahead(content)

Put content in front of the reader while the route that calls it is still running. Under the default :auto OperationPolicy a route that takes longer than its grace period answers with a progress poller; each part sent ahead lands once, in the order sent, in a region above that poller's progress tree, and the route's finished answer replaces the parts together with the poller. content is anything a route may return (a Node, a string, a vector of them), rendered to HTML when send_ahead is called.

serve_key_feed!(sse::SSEStream, subs::KeySubscriptions, key; poll=1.0) -> Nothing serve_key_feed!(sse::SSEStream, subs::KeySubscriptions, keys::AbstractVector; poll=1.0) -> Nothing

@sse route body for a keyed subscription feed: subscribes sse to key (or every key in keys), blocks while the client stays connected, and unsubscribes on the way out. poll is the disconnect-check interval in seconds.

HTMXObjects.sse_region Method

sse_region(url, content...; events="message,done", close="close", swap=nothing)

Client side of an @sse route: a <div hx-ext="sse" sse-connect=url> that opens the stream, wrapping a target that swaps in the named events (default: plain sends and the body's final done value). The source closes on the framework's close event, so a finished stream is not re-run by the browser's automatic reconnect. content is the target's initial content; swap sets its hx-swap (htmx's default replaces the inner HTML; pass swap="beforeend" to append a log or feed).

source
HTMXObjects.stream_probe_script Method

stream_probe_script()

Client runtime that lets an auth gateway end a refused stream. A browser exposes no HTTP status for a refused WebSocket handshake (just error and close 1006) or a refused EventSource (it ends CLOSED), so a stream behind an expired login cannot tell a 401 from a transient failure: the htmx ws and sse extensions reconnect with backoff forever, and the page goes stale until a manual reload.

subscribe_key!(subs::KeySubscriptions, sse::SSEStream, key) -> String

Register sse for push refreshes of key (converted with string, which must be non-empty). Registering the same stream twice is a no-op. Returns the key. serve_key_feed! calls this for @sse route bodies; call it directly only for a hand-rolled feed.

system_load_panel(load_url; interval="2s", attrs...)

A self-refreshing fragment showing load average, current process RSS, live Julia heap and system memory. Serve it from load_url. It uses the same measurements as runtime_snapshot().process and pauses polling in hidden tabs. Extra attributes belong to its outer element. No garbage collection runs while rendering it.

HTMXObjects.track_job! Method

track_job!(handle; label=nothing, progress=nothing, req=nothing, tracker=nothing) -> Int

Record work that HTMXObjects' operation layer did not start as a job, so it shows on the runtime dashboard and on jobs_boards: a compute behind a hand-rolled Treebars.polling_fetchindex poller (which calls this itself), an app's Threads.@spawn, a warm-up task. handle is the in-flight work — a DynamicObjects Pending, a Task, or anything fetch waits on — and a watcher stamps its outcome (:done, or :failed with the error's summary) when it resolves. progress is its progress node (a Treebars tree), label its name (default "Job").
